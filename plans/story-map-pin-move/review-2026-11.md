## 한눈에

- **관점**: 플레이어 경험 → 기획자 작업 효율 → 문서 읽기 쉬움 순으로 봤다. 새 기능은 넣지 않고 지금 범위 안에서 다듬었다.
- **결과**: 14곳을 고쳤다. 가장 큰 것은 **폰에서 글자가 너무 작아지는 문제**와 **기획자 여러 명이 같은 품질로 만드는 기준**이다.
- **문서**: 연출 기획서를 본문(10분)과 부록으로 나눴고, 리드·PD 회의용 한 장을 새로 만들었다.
- **결정 필요**: 4건. 맨 아래에 있다. 새로 정한 값은 모두 `검증필요`로 두었다.

## 어떻게 검토했나

1. **플레이어로 보기**: 프로토를 폰 가로 크기로 놓고 장면 1 → 대사 → 장면 2 → 닫기를 따라가며 "누가 어디서 어디로"가 읽히는지 봤다.
2. **기획자로 보기**: 스토리 기획자 여러 명이 같은 배경과 장소를 나눠 쓰며 연출을 만든다고 놓고, 막히는 곳·서로 망가뜨리는 곳·품질이 갈리는 곳을 봤다.
3. **리드로 읽기**: 본문만 읽고 무엇을 만드는지 알 수 있는지, 담당자가 필요한 곳을 바로 찾는지 봤다.
4. **정합성 점검**: 규칙 ID, 설정 키 수치, 예시 데이터, 프로토, 인계 파일이 서로 같은지 스크립트로 확인했다.

## 바꾼 것: 문서 읽기 쉬움

| 무엇이 문제였나 | 무엇을 바꿨나 |
|---|---|
| 기획서가 820줄이라 리드가 어디까지 읽어야 하는지 알 수 없었다. | 본문(무엇을 만드는지)과 부록 A~I(데이터, 설정 키, 계산식, 예시, 예외, 회사 데이터 연결, 구현, 검수, 작업 목록)로 나눴다. 「누가 어디를 읽나」 표를 다시 썼다. 규칙 ID는 하나도 바꾸지 않았다. |
| 글로만 설명해서 화면이 머리에 안 그려졌다. | 본문 앞쪽에 「플레이어가 보는 장면」을 두고 게임 화면 컷 4장과 유저가 읽는 순서를 넣었다. |
| 「연출」「연출 맵」「장면」이 섞여 있었다. | 한 건은 「연출」, 「장면 1」은 예시 이름으로만 쓴다. |
| 툴 기획서도 표가 길었다. | 속성 패널 저장 위치, 검사 항목, 작업 목록을 부록으로 옮겼다. |
| 리드·PD에게 보여줄 자료가 없었다. | 회의용 한 장을 새로 만들었다: 왜 필요한가, 유저가 보는 장면, 범위, 만드는 쪽 규모, 위험, 회의에서 정할 것. |

## 일부러 안 바꾼 것

| 항목 | 이유 |
|---|---|
| 연출 템포(등장 800ms, 마무리 1000ms, 탭 완료 300ms) | 메인 스토리에서 가끔 나오는 연출이라, 한 번 볼 때 여유 있게 읽히는 지금 템포가 맞다. 실제 기기에서 설정 키로 조정한다. |
| 지도 전체를 보이게 하는 방식(R-19) | 확정된 규칙이다. 넓은 폰의 좌우 여백은 다음 버전 후보로 남겼다. |
| 도착 표시 없음 | 확정된 방향이다. 도착은 장소 마크와 멈춘 핀으로 읽는다. |
| 앞 궤적 단 수의 동작 | 확정된 동작이라 바꾸지 않고 설정 키로만 뺐다. 결정 필요 1번. |
| 카메라 연출 | 기능 완성 후 재검토로 이미 정했다(R-16). |
