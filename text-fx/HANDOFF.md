# 회사 Claude 인수인계: 텍스트 연출 효과 (드롭 / 상승 / 그라데이션)

이 폴더는 게임 텍스트 연출 3종의 기획서 초안과 동작 시안이다. 회사 내부 기획서(규격), 기획 데이터, 클라이언트·서버 코드를 보고 기획서를 다듬는 것이 다음 작업이다.

## 파일

| 파일 | 내용 |
| --- | --- |
| `spec.md` | 기획서 본문. 이 파일이 기준이다 |
| `index.html` | 동작 시안(단일 HTML, 브라우저에서 바로 열린다). 프리셋 값은 이 파일의 `PRESETS`와 `spec.md`의 프리셋 정의표가 일치한다 |

## 이미 정해진 것 (바꾸지 말고, 코드와 충돌할 때만 보고)

`spec.md`의 "확정 사항"과 본문에서 `(확정)`이 붙은 항목은 기획자가 직접 결정한 내용이다. 내부 규격이나 코드와 충돌하면 임의로 고치지 말고, 어떻게 충돌하는지 정리해서 기획자에게 물어본다.

- 태그는 기존 `<$이름>…</$이름>` 규칙을 쓰고, 기획자는 프리셋 이름만 고른다. 세부 값은 프리셋 표에 있고 수정은 플머만 한다.
- 프리셋 이름: `drop_s/m/l`, `rise_s/m/l`, 그라데이션은 `grad_op`, `grad_tl`, `grad_yr`.
- 분신은 원본 글자의 복제본이 떨어지거나(드롭) 올라가는(상승) 방식이다. 물방울은 쓰지 않는다.
- 효과 대사는 타자 연출 없이 페이드인으로 나타나고 즉시 시작해 대사가 떠 있는 동안 반복한다. `delay`·`time` 값은 두지 않는다.
- 접촉 반응은 같은 텍스트 id(Yuna text) 안의 글자끼리만 일어난다.
- 그라데이션은 기존 색상 변경 태그와 같은 취급이다. 글자를 움직이는 효과끼리(드롭, 상승, 기존 `wave` 등)는 겹쳐 쓸 수 없고, 겹치면 안쪽만 적용하고 경고한다.
- 오른쪽에서 왼쪽으로 쓰는 언어는 지원하지 않는다.

## 코드와 내부 문서를 보고 확인할 것

우선순위 순서다.

1. **기존 태그 처리 코드**: `<$wave_s>` 같은 태그를 파싱하고 렌더링하는 곳을 찾아, 새 프리셋을 어디에 어떻게 붙일지 확인한다.
   - 없는 프리셋 이름, 닫히지 않은 태그, 빈 태그를 기존 코드가 어떻게 처리하는지. 기획서 규칙 표에 "확인 필요"가 두 군데 있다. 기존 방식이 있으면 그것에 맞춰 문구를 바꾼다.
   - 규격 이름(`s`, `m`, `l`)과 이름 규칙이 내부 규격과 맞는지. 맞는다고 기획자가 확인했지만, 코드에서 실제 충돌이 보이면 알려준다.
2. **글자 분할 기준 (미결 1)**: 이모지와 결합 문자를 사용자가 보는 한 글자 단위로 묶어 나누는 기능을 엔진과 폰트가 지원하는지 확인한다. 안 되면 대안을 제안한다.
3. **동시 대사 수와 성능 상한 (미결 2)**: 효과 대사는 한 화면에 여러 개 뜰 수 있다는 것만 정해졌다. 실제 화면 구성에서 몇 개까지 동시에 뜨는지, 화면 전체의 분신 수 상한을 어디에 둘지 제안한다. 시안은 분신 최대 16개, 분신당 잔상 최대 4개로 만들었고 실기기 성능은 측정하지 않았다.
4. **서버·데이터 쪽**: 대사 텍스트가 어떤 형식으로 저장되고 전달되는지(태그가 그대로 들어가는지, 번역 파이프라인을 거치는지). 기획서는 번역 도구가 태그를 보호하고 짝을 검사한다는 전제다.
5. **기획서 문서 자체**: 내부 기획서 양식과 용어, 문서 구조에 맞게 다듬는다. 구현 참고(플머용) 절은 실제 코드 구조에 맞춰 고친다.

## 작업 방식 (요청)

- 기획서를 고칠 때는 무엇을 왜 바꿨는지 목록으로 남긴다.
- 확정 사항을 바꾸고 싶으면 바꾸지 말고 "제안"으로 따로 적는다.
- 모르는 것은 추측해서 채우지 말고 미결로 남긴다. 기획자도 모르는 건 모른다고 했다.
- 시안(`index.html`)의 프리셋 값을 바꾸면 `spec.md`의 프리셋 정의표도 같이 바꾼다. 둘이 어긋나지 않게 한다.
