# 기획 문서·시안 만들기

기준 샘플: `assets/spec-sample.html` (사용자가 디자인 방향을 확인함). 새 문서는 이 샘플의 구조와 스타일을 복제해서 시작한다. 색·폰트·간격을 임의로 바꾸지 않는다.

## 0. 빌드 도구 (spec.md → spec.html)

`spec.html`은 직접 쓰지 않고 스크립트로 만든다. 폴리싱 때 md만 고치면 되어서 폰 작업에 맞다.

```bash
python3 tools/build_spec.py plans/<슬러그>                       # spec.html 생성
python3 tools/build_spec.py plans/<슬러그> --artifact <경로>.html  # Artifact 게시용 조각도 생성
python3 tools/artifact_fragment.py 입력.html 출력.html            # proto, mockups, summary 를 게시용 조각으로 변환
```

- 필요 패키지: `pip install markdown`
- spec.md 작성 규칙은 `tools/build_spec.py` 맨 위 설명을 따른다(front matter, `{확정}` `{검증필요}` `{미정}` 배지, `[[svg:파일]]` 흐름도, `>` 전달사항 박스).
- 게시용 조각은 스크래치패드에 만들고 Artifact로 올린다. 저장소에는 넣지 않는다.
- 시안·요약처럼 같은 그림을 여러 번 쓰는 HTML은 기획 폴더의 `src/` 생성 스크립트로 만든다. 예: `plans/story-map-pin-move/src/gen_visuals.py`
- 기능이 커서 툴 기획이 따로 필요하면 별도 기획 폴더로 나누고 서로 참조한다. 예: `plans/map-move-tool/`
- 참고 사례: `plans/story-map-pin-move/` (spec.md, flow.svg, mockups, proto, summary 한 세트)

## 1. spec.md 구조

| 순서 | 섹션 | 내용 |
|---|---|---|
| 1 | 개요 | 목적, 대상 유저, 범위(이번 버전에 포함/제외) |
| 2 | 핵심 규칙 | ID(R-01…), 규칙, 상태 배지 |
| 3 | 처리 흐름 | 상태·전이·조건. 흐름도 SVG |
| 4 | 수치표 | 확률, 비용, 보상, 기간. 상태 배지 |
| 5 | 연출 타임라인 | 연출 기획일 때만. 아래 표기 참고 |
| 6 | 예외 처리 | 상황, 처리, 메시지 |
| 7 | 구현 전달사항 | 프로그래머에게 하는 말. 테이블 분리, 상수화, 로그 |
| 8 | 아트 전달사항 | 필요한 리소스, 사이즈, 개수. 아트팀 대상일 때만 |
| 9 | 검증·미결 목록 | 회사 데이터로 확인할 것, 결정 대기 |

문서 상단에 버전, 작성, 구현 대상, 검증필요 건수를 넣는다. 건수는 표의 검증필요/미정 행 수와 일치해야 한다.

## 2. 상태 배지 (모든 문서 공통)

- `확정` 초록: 사용자가 확정했다고 말한 것만
- `검증필요` 주황: 가정한 값, 회사 데이터 확인 전
- `미정` 보라: 결정 대기

표의 행에 상태가 있으면 `data-s="ok|warn|tbd"` 속성을 붙인다. 샘플의 "검증필요·미정만 강조" 버튼이 이 속성을 쓴다.

## 3. 연출 타임라인 표기

연출 기획에는 시간 순서가 핵심이다. 표로 쓴다.

| 시점(초) | 지속(초) | 대상 | 동작 | 이징 | 사운드 | 비고 |
|---|---|---|---|---|---|---|
| 0.0 | 0.3 | 카메라 | 줌인 1.0→1.15 | ease-out | - | |

- 시점은 연출 시작 기준 초 단위, 소수 한 자리까지.
- 총 길이, 스킵 가능 여부, 반복 재생 규칙을 표 위에 명시한다.
- 가능하면 `proto/`에 같은 타임라인을 재생하는 프로토타입을 붙인다.

## 4. 디자인 규칙

샘플을 기준으로 한다. 핵심만 요약한다.

- 레이아웃: 데스크톱은 좌측 고정 목차 + 본문. 860px 이하는 상단 칩 목차.
- 타이포: 본문 Noto Sans KR 15px/1.7, 데이터·ID는 JetBrains Mono. 폰트 대체 스택 필수.
- 색: 모든 색을 `:root` 토큰으로 정의. 라이트·다크 모두 정의하고 `body` 배경을 토큰으로 지정.
- 장식 금지: 그라데이션 히어로, 이모지 섹션 표식, 둥근 카드 남발 금지. 표·간격·위계로 승부한다.
- 표: `overflow-x:auto` 컨테이너 안에. 숫자 열은 오른쪽 정렬, `tabular-nums`.
- 흐름도: 인라인 SVG, `viewBox` 사용, 색은 토큰만 사용.
- 단일 파일. 외부 이미지·스크립트 라이브러리 금지.

## 5. 화면 시안 (mockups/)

- 아트팀에 보여주는 용도. 정적 화면을 HTML/CSS로 그린다.
- 폰 화면 비율(예: 9:19.5) 프레임 안에 그리고, 화면별로 영역 이름과 치수 주석을 붙인다.
- 같은 화면의 상태 변형(기본/보상 획득/잠김 등)을 나란히 보여준다.
- 아직 없는 리소스는 회색 플레이스홀더에 "ICON 128×128"처럼 필요한 규격을 쓴다.
- 확정되지 않은 레이아웃이면 화면 위에 `검증필요` 배지를 둔다.

## 6. 동작 프로토타입 (proto/)

- 목적은 "이렇게 움직인다"를 프로그래머·아트팀이 눌러보고 이해하는 것이다. 완성도보다 의도 전달이 우선이다.
- 단일 HTML, 바닐라 JS와 CSS 애니메이션/canvas로 구현한다.
- 조작 UI를 항상 붙인다: 재생/일시정지, 속도(0.25x/0.5x/1x), 타임라인 스크럽, 처음으로.
- 수치 파라미터(길이, 확률, 속도 등)는 화면 옆 패널에서 조절 가능하게 하고, 값 옆에 상태 배지를 단다.
- 폰 터치로 조작 가능해야 한다(버튼 최소 44px).
- 프로토타입의 값과 `spec.md`의 값을 일치시킨다. 다르면 spec이 기준이다.

## 7. 한 장 요약 (summary.html)

- 한 화면에 목적 / 핵심 규칙 3~5개 / 가장 중요한 수치 / 일정·범위 / 결정 필요 사항.
- 스크롤 없이 데스크톱 한 화면에 들어오는 것을 목표로 한다.
- 설명을 줄이고 숫자와 상태 배지로 보여준다.

## 8. 제출 전 점검

- [ ] 모든 값에 상태 배지가 있다
- [ ] 문서 상단 검증필요 건수가 표와 일치한다
- [ ] 400px 폭에서 본문이 가로 스크롤 없이 읽힌다
- [ ] 라이트·다크 모두 읽힌다
- [ ] 외부 리소스가 없다(구글 폰트 제외)
- [ ] spec.md와 spec.html의 내용이 같다
