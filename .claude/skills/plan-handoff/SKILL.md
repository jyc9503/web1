# 회사 검토용 인계 파일 (HANDOFF.md)

이 저장소는 회사 데이터를 볼 수 없다. 회사 PC의 회사 계정 Claude가 `spec.md`와 `HANDOFF.md`를 읽고, 회사 데이터 기준으로 검토하고 기획을 수정한다. 그 Claude는 이 대화를 모른다. 파일만으로 상황을 이해할 수 있어야 한다.

## HANDOFF.md 구성

```markdown
# <기획명> 회사 검토 요청 (v0.x)

## 이 문서가 무엇인가
이 기획이 무엇이고 지금 어느 단계인지 3~5줄.
이 기획은 회사 외부에서 회사 데이터 없이 작성되었다.

## 먼저 읽을 파일
- spec.md : 기획서 원본 (수정은 여기서)
- decisions.md : 확정된 결정
- proto/, mockups/ : 시안과 프로토타입 (있다면)

## 건드리면 안 되는 것 (확정)
- 규칙 ID와 한 줄 요약. 사용자가 확정한 것만.

## 검증해 주세요 (검증필요)
| ID | 가정한 내용 | 무엇과 비교할지 | 바꿔도 되는 범위 |
|---|---|---|---|
| R-03 | 파괴 시작 +10 | 기존 유사 시스템의 실패 페널티 | 단계 ±2 |

## 결정이 필요합니다 (미정)
- ID, 선택지, 이 기획자(작성자)가 기울어 있는 안

## 회사 Claude에게 요청하는 작업
1. 위 표의 각 항목을 회사 데이터와 비교해 일치/불일치/데이터 없음으로 판정한다.
2. 불일치하면 수정안과 근거를 제시한다.
3. spec.md를 수정하고 버전을 올린다. 상태 배지를 갱신한다.
4. 변경 내역을 CHANGES.md에 정리한다.

## 규칙
- 확정 항목은 바꾸지 않는다. 충돌하면 수정하지 말고 CHANGES.md에 질문으로 남긴다.
- 회사 비공개 수치는 문서에 직접 쓰지 말고 "회사 데이터 기준 반영"처럼 쓰고, 필요한 값만 기획자에게 직접 전달한다.
```

## 작성 순서

1. `spec.md`에서 상태가 `검증필요`/`미정`/`확정`인 항목을 전부 수집한다.
2. 검증필요 항목마다 **무엇과 비교할지**와 **바꿔도 되는 범위**를 직접 정한다. 비교 대상을 모르면 "관련 수치 전반"이라고 쓰지 말고, 후보 데이터 종류를 구체적으로 적는다.
3. 위 구성대로 `HANDOFF.md`를 쓰고, 회사 Claude에게 붙여넣을 한 줄 지시문을 대화에 함께 준다.
4. 커밋·푸시하고 브리핑한다.

## 회사에서 수정본이 돌아왔을 때

사용자가 수정된 `spec.md`나 `CHANGES.md`를 가져오면 다음 순서로 처리한다.

1. 변경점을 요약해 브리핑한다(바뀐 규칙 ID, 상태 변화, 질문으로 남은 항목).
2. `spec.md`를 새 버전으로 반영하고 `decisions.md`를 갱신한다.
3. `spec.html`과 시안, 프로토타입의 값을 새 spec에 맞춰 다시 만든다.
4. 회사 비공개 값이 문서에 직접 들어 있으면 사용자에게 알려 주고, 이 저장소(GitHub)에 올릴지 먼저 확인한다.

## 보안 주의

회사 기밀 수치가 이 저장소에 올라가면 외부 서비스에 저장된다. 회사 데이터는 올리지 않는 것이 기본이다. 수정본을 반영할 때도 실수치가 들어 있으면 올리기 전에 사용자에게 확인한다.
